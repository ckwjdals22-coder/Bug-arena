# 부하 테스트 결과

> 측정일 2026-11-27. 여기 적힌 숫자는 **아래 조건에서 실제로 잰 값**이며, 그 밖의 조건(실제 인터넷, 실제 휴대폰, 다른 서버 사양)에 대한 보장이 아닙니다. "1만 명 동시접속 보장" 같은 주장은 하지 않습니다.

## 1. 어떻게 쟀나

- 도구: `tools/loadtest.ts` (`npm run loadtest -- --url ws://localhost:8830 --rooms N --bots 20 --seconds 45`)
- 봇은 사람과 **같은 프로토콜**로 접속한다: `hello` → 10Hz 이동 패킷(충돌 처리 포함 무작위 걷기) → 몇 초마다 이모트 또는 가까운 시민에게 말 걸기·멘트 선택 → 4초마다 ping.
- 서버: 운영용 번들(`node dist/server/main.js`) **프로세스 1개**, 방마다 NPC 28명을 10Hz로 시뮬레이션.
- 기계: 4 vCPU(Intel Xeon 2.1GHz) 가상 머신 1대. **서버와 봇이 같은 기계에서 돌았고**, 측정 중 다른 개발 작업도 일부 돌고 있었다(부하 평균 1.1~3.5). 즉 서버에 불리한 조건이다.
- 서버 수치는 `/healthz`(틱 시간 p95·최대, 메모리, 누적 CPU 시간)에서 읽었다.

읽는 법

- 틱 예산은 100ms(10Hz)다. 틱 시간이 이 안에 들어오면 시뮬레이션이 밀리지 않는다.
- 100방까지는 스냅샷이 초당 10개 그대로 나갔다. 150방에서는 9.6개로 떨어지기 시작했고 CPU가 코어 하나의 90%에 닿았다. **이 기계에서 프로세스 1개의 실용 한계는 150방 근처**로 본다.
- 클라이언트 1명이 받는 양은 방 수와 무관하게 약 3.2KB/s(시간당 약 11.5MB)다. 위치는 바이너리(플레이어 8바이트, NPC 7바이트)로, 변한 것만, 같은 방에만 보낸다.
- 네 측정 모두에서 서버의 위치 보정(`pos`)은 0건이었다(정상 이동은 서버 검증에 걸리지 않는다). 측정 중 봇들은 실제로 말을 걸고 포교했다(예: 100방 측정에서 말 걸기 2,107회, 합류 629회).

## 3. 검증하지 못한 것

- **실제 브라우저·실제 GPU.** 봇은 렌더링을 하지 않는다. 화면 성능은 헤드리스 Chromium(소프트웨어 렌더링)으로만 확인했고 실제 휴대폰에서는 재지 않았다.
- **실제 네트워크.** 전부 localhost 다. 지연·패킷 손실·모바일 망 전환, TLS(wss) 비용, 프록시/로드밸런서의 연결 제한은 포함되지 않았다.
- **장시간 운영.** 각 측정은 약 45초(150방은 40초)다. 메모리 누수나 며칠 단위의 안정성은 확인하지 않았다.
- **여러 대 구성.** 프로세스 1개만 쟀다.
- **사람의 실제 행동.** 봇은 계속 걷고 자주 말을 건다(사람보다 메시지가 많은 편). 반대로 한곳에 20명이 몰려 춤추는 식의 쏠림은 흉내 내지 않았다.

## 4. 운영 지침(측정에 근거한 권고)

- **1차 목표(방 3개 × 20명):** 가장 작은 서버(1 vCPU, 512MB~1GB)로 충분하다. 비용을 정하는 것은 CPU 가 아니라 **전송량**이다 — 방 3개가 한 달 내내 가득 차면 약 500GB.
- **방 100개까지:** 프로세스 1개로 가능했다(코어 하나의 63%). 여유를 두려면 2 vCPU 이상, 메모리 1GB 이상, 월 전송량 한도를 꼭 확인한다(2,000명 상시 접속 시 초당 약 52Mbit).
- **그 이상:** Node 는 한 프로세스가 코어 하나만 쓴다. 150방 근처에서 한계가 오므로 **프로세스(또는 서버)를 늘리고 방 번호로 나눠 보낸다.** 방끼리는 상태를 공유하지 않으므로 "방 1~100 → 서버 A, 101~200 → 서버 B" 식의 고정 분배가 가능하다. 지금 코드에는 이 분배기가 없다(§5).
- 자동 증설: `ROOMS=3 MAX_ROOMS=100` 처럼 주면 모든 방이 80% 이상 찼을 때 다음 방을 미리 만들고, 늘어난 방이 5분 넘게 비면 정리한다. 기본값은 증설 꺼짐(`MAX_ROOMS = ROOMS`).
- 인스턴스는 **반드시 1개**(호스팅의 자동 확장 끄기). 방 상태가 메모리에 있어서 인스턴스가 둘이 되면 "1번 방"이 두 개가 된다.

## 5. 아직 없는 것

- 여러 서버에 방을 나눠 주는 로비/라우터(방 번호 → 서버 주소). 설계상 `GET /api/rooms` 가 방마다 접속 주소를 알려 주도록 확장하면 된다.
- 서버 간 교단 순위 합산. 지금은 프로세스 1개 기준이다.
- Cloudflare Durable Objects 구성에서의 부하 측정(`docs/DEPLOY-CLOUDFLARE.md` 참고).

## 6. 직접 재 보기

```bash
npm run build
PORT=8830 ROOMS=100 node dist/server/main.js &
npm run loadtest -- --url ws://localhost:8830 --rooms 100 --bots 20 --seconds 45 --ramp 30
```

도구는 남의 서버를 두드리지 않도록 localhost 가 아니면 실행을 거부한다. 직접 운영하는 서버를 재려면 `--i-own-this-server` 를 붙인다. 봇은 `봇123` 같은 이름의 시험용 접속자로 보이므로 실제 이용자가 있는 방에는 넣지 않는다.
